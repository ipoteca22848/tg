# Код сайта для вашего хостинга

Веб-версия и установленные клиенты используют один Supabase-проект. Установленным APK/EXE не требуется запускать этот сайт или держать браузер открытым.

## Обычный статический хостинг

Скопируйте содержимое папки `docs/` в корень сайта. Нужен HTTPS. Сборка Node.js на хостинге не требуется — `docs/app.js` уже собран.

## Docker на VPS

Из корня исходников выполните:

```sh
docker compose up -d --build
```

Сайт будет слушать порт 8080. Настройте HTTPS у вашего reverse proxy или панели хостинга. Приложения подключаются к Supabase напрямую, этот сайт не является прокси для сообщений.

## Сервер и база

Действующий backend — ваш Supabase-проект `companion-messenger`. Регистрация, аккаунты, переписка и покупки подарков хранятся там. Файлы в `supabase/` содержат SQL-схему, RLS и код регистрации.

Для другого Supabase-проекта примените в таком порядке:

1. `supabase/schema.sql`
2. `supabase/profile-fields.sql`
3. `supabase/profile-gifts.sql`
4. `supabase/gift-catalog.sql`
5. `supabase/chat-media.sql`

Разверните Edge Function `supabase/functions/register/index.ts` с проверкой JWT. `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` используются только в окружении Edge Function, не в сайте.

В `docs/companion-config.js` задайте публичные URL, publishable key и legacy anon JWT для вызова Edge Function. Это публичные параметры, а не административные секреты. Не помещайте service-role ключ в этот файл.

Для использования другого backend установленными приложениями отредактируйте публичную конфигурацию до сборки APK/EXE. Для обновления нужно выпустить новую сборку.

Публичный endpoint регистрации поддерживает CORS без cookie. Права на данные проверяет Supabase Auth/RLS; произвольный Origin не даёт права менять чужие аккаунты, балансы или роли.

## Локальная проверка сайта

```sh
python3 -m http.server 4173 --directory docs
```

Звёзды и TON в этой реализации — тестовые единицы без денежной стоимости; реальные платежи не подключены. Все исходники кроме публичной конфигурации должны оставаться вне document root хостинга.

Медиа переписки используют закрытый bucket `chat-media`. При собственном reverse proxy разрешите `media-src` для вашего Supabase-домена. Для записи микрофона сайт должен быть открыт по HTTPS; на loopback-адресе браузер допускает локальную проверку.

## Звонки между разными сетями

Чаты, вложения и подарки работают через Supabase между Wi-Fi и мобильными сетями. Звонки используют WebRTC: без TURN доступны прямые соединения, которые могут не пройти за CGNAT, строгим NAT или сетевым экраном. Supabase и GitHub Pages не заменяют TURN. TURN в текущей конфигурации **не размещён**. Даже с TURN сети, полностью блокирующие медиа, могут мешать звонкам.

Для надёжного соединения нужен публичный Linux VPS или поставщик TURN. Пример `host/turn/compose.yaml` запускает coturn на VPS с host networking. Скопируйте `.conf.example` в `turnserver.conf`, замените IP/домен/секрет, положите TLS-сертификат и ключ в `certs`, откройте TCP/UDP 3478, TCP 5349 и UDP 49160–49260. При NAT у VPS укажите `external-ip=PUBLIC_IP/PRIVATE_IP`. Для сетей, разрешающих лишь TLS 443, выделите отдельный IP/хост для TURN TLS на 443; один nginx с HTTP proxy этого не обеспечивает.

Разверните `supabase/functions/turn-credentials/index.ts` с проверкой JWT. В секретах функции задайте `TURN_SHARED_SECRET` (совпадает с coturn), `TURN_URLS=turn:turn.example.com:3478?transport=udp,turn:turn.example.com:3478?transport=tcp,turns:turn.example.com:5349?transport=tcp`. Секрет создайте через `openssl rand -hex 32`. В `docs/companion-config.js` добавьте `turnCredentialsUrl` с HTTPS-адресом этой функции. Клиент получит временные credentials только после входа. Не публикуйте общий секрет в JS. Пересоберите APK/EXE после изменения конфигурации. Для проверки ретрансляции временно задайте `relayOnly: true`, проверьте два устройства в разных сетях и затем верните `false`.

Входящие вызовы работают, пока Companion открыт; фоновые push-вызовы не реализованы. Android при уходе приложения в фон завершает звонок и освобождает камеру/микрофон. Видео и звук звонков не сохраняются сервером. Прямое WebRTC-соединение раскрывает IP собеседнику; `relayOnly: true` с рабочим TURN использует ретрансляцию.

Дополнительно примените после `chat-media.sql`: `calls.sql`, `currency-gifts.sql`, `gift-expansion.sql`. Переводы звёзд и тестовых TON атомарны и защищены от повторного начисления. Удаление карточки из чата не отменяет перевод и не удаляет запись внутреннего перевода.

## Админ-панель (0.8)

После остальных SQL-файлов примените `supabase/admin.sql` и разверните Edge Function `supabase/functions/admin/index.ts` с `verify_jwt=true`. Функция использует стандартные серверные SUPABASE_URL и SUPABASE_SERVICE_ROLE_KEY; их не нужно и нельзя помещать в клиент. Включение клиентской кнопки не даёт прав: Edge Function проверяет реальную текущую роль, а служебные SQL-функции недоступны authenticated/anon.

Создатель выдаёт роль admin; роль creator через панель не выдаётся. Администраторы не управляют создателем, другими администраторами или ролями. Профили и административные действия журналируются. Таблица `companion_private.admin_changes` резервирует аккаунт на время согласования номера с Supabase Auth; при обычной ошибке Auth/профиля выполняется откат. Если внешний вызов Auth или Edge Function аварийно прервётся в середине операции, запись резерва сохраняется: сверьте `before_profile`, `patch`, фактический email в Auth и номер профиля перед восстановлением. Не удаляйте резерв и не повторяйте изменение вслепую. Это предотвращает параллельную рассинхронизацию, но не является распределённой транзакцией с Auth.

Бан защищён restrictive RLS и проверками в привилегированных RPC. Старые JWT не дают заблокированному пользователю читать переписку, писать сообщения, дарить или звонить. Уже скачанные файлы не удаляются с устройства; ранее выданная подписанная ссылка на файл может оставаться действительной до её истечения. Администраторы не получают доступ к личной переписке через панель.
