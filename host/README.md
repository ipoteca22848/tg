# Код сайта для вашего хостинга

Веб-версия и установленные клиенты используют один Supabase-проект. Установленным APK/EXE не требуется запускать этот сайт или держать браузер открытым.

## Обычный статический хостинг

Скопируйте содержимое папки `docs/` в корень сайта. Нужен HTTPS. Сборка Node.js на хостинге не требуется — `docs/app.js` уже собран.

## Docker на VPS

Из корня исходников выполните:

```sh
docker compose up -d --build
```

Сайт будет слушать порт 8080. Настройте HTTPS у вашего reverse proxy или панели хостинга. Приложения подключаются к Supabase напрямую, этот сайт не является прокси для сообщений.

## Сервер и база

Действующий backend — ваш Supabase-проект `companion-messenger`. Регистрация, аккаунты, переписка и покупки подарков хранятся там. Файлы в `supabase/` содержат SQL-схему, RLS и код регистрации.

Для другого Supabase-проекта примените в таком порядке:

1. `supabase/schema.sql`
2. `supabase/profile-fields.sql`
3. `supabase/profile-gifts.sql`
4. `supabase/gift-catalog.sql`

Разверните Edge Function `supabase/functions/register/index.ts` с проверкой JWT. `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` используются только в окружении Edge Function, не в сайте.

В `docs/companion-config.js` задайте публичные URL, publishable key и legacy anon JWT для вызова Edge Function. Это публичные параметры, а не административные секреты. Не помещайте service-role ключ в этот файл.

Для использования другого backend установленными приложениями отредактируйте публичную конфигурацию до сборки APK/EXE. Для обновления нужно выпустить новую сборку.

Публичный endpoint регистрации поддерживает CORS без cookie. Права на данные проверяет Supabase Auth/RLS; произвольный Origin не даёт права менять чужие аккаунты, балансы или роли.

## Локальная проверка сайта

```sh
python3 -m http.server 4173 --directory docs
```

Звёзды и TON в этой реализации — тестовые единицы без денежной стоимости; реальные платежи не подключены. Все исходники кроме публичной конфигурации должны оставаться вне document root хостинга.
